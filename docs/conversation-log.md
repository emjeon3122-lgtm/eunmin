# 대화 기록 — 사내 경조사 화환 자동 발송 앱 개발

날짜: 2026-08-26 · 참여자: 은민님(BDO KOREA), Claude

> 이 파일은 대화의 흐름과 각 시점에 오간 내용을 정리한 기록입니다. 실제로 만들어진 4개 설계 문서(01~04단계)는 별도 파일로 이미 전달드렸으며, 이 로그에는 문서가 만들어지고 수정된 시점과 그 이유를 함께 적어두었습니다.

## 1. 시작 — 프롬프트 검토 요청

**은민님**: 안녕. 어플 개발을 할 생각이야. 내가 프롬프트를 써왔는데, 전달할게 봐줄래?

이어서 "사내 경조사 화환 자동 발송 요청 애플리케이션 개발"이라는 제목의 상세 요구사항 문서를 공유함. 프로젝트 개요, 핵심 사용자(일반 임직원/관리자), 화환 신청 필수 입력 항목, 꽃집 연동 방식(Webhook/API 또는 이메일·알림톡), 추천 기술 스택(Next.js, NestJS/FastAPI, PostgreSQL 등), 그리고 5단계 개발 가이드 요청(①아키텍처 ②DB ③API ④프론트엔드 ⑤백엔드 연동)이 포함되어 있었음.

**Claude**: 프롬프트 전반적으로 잘 짜여 있다고 평가하면서도, 개발 착수 전에 정해두면 좋을 지점들을 짚음 — 꽃집이 여러 곳일 때 매칭 방식, 승인 절차가 조건부인지, 로그인 SSO 공급자, React/React Native 중 우선순위. 이 외에도 개인정보 보관, 중복 신청 방지, 리드타임 검증 등을 참고사항으로 언급.

이어서 4가지 핵심 질문을 드림:
- 인증 방식 → **회사 SSO 연동**
- 승인 절차 → **모든 신청 사전 승인 필수** (이후 2번 대화에서 뒤집힘, 아래 참고)
- 꽃집 매칭 방식 → **계약된 곳은 1곳**
- 플랫폼 → **반응형 웹 우선**

## 2. 1단계: 시스템 아키텍처 & DB 설계

위 답변을 바탕으로 `01-architecture-and-db.md`를 작성해 전달. 신청 제출 → 관리자 승인 → 꽃집 전달 → 배송 상태 추적의 흐름과 ERD(users, wreath_requests, approvals, vendors, products 등)를 구성함.

### 2-1. "승인 없애고 싶다"

**은민님**: 관리자(총무·HR) 업무를 덜기 위해 앱을 만드는 건데, 승인 필수는 원래 목표와 안 맞는다. 승인 없이 진행하는 걸로 바꿔달라. 대신 사전 승인이 필요한 경우엔 본부장 승인 증빙을 첨부해야만 제출 가능하게 하고 싶다.

**Claude**: 확인 질문 두 가지를 드림 — 사전승인 필요 여부를 어떻게 판단할지(자기선언 vs 규칙 기반) → **규칙 기반(금액/유형)** / 관리자가 사후에 취소할 수 있어야 하는지 → **사후 취소 가능**.

이에 맞춰 문서를 대폭 수정: `approvals` 테이블 제거, `attachments`(증빙 파일)와 `approval_rules`(판정 기준) 테이블 추가, 상태 흐름을 `draft → submitted → submitted_to_vendor → in_delivery → completed`로 변경. 관리자 역할을 "승인자"에서 "사후 감사자"로 재정의.

### 2-2. 꽃집 연동 채널 — 카카오톡

**은민님**: 꽃집 전달 과정은, 우리 법인 카카오톡 비즈니스 채널을 만들어서 꽃집한테 카카오톡으로 전송할 생각이다.

**Claude**: 알림톡과 친구톡의 차이(템플릿 사전심사 필요 여부, 자동 SMS 대체발송 여부)를 설명하고, 꽃집이 채널 친구가 아닐 가능성이 높으니 알림톡을 권장한다고 안내. `vendors`, `order_transmissions` 테이블에 카카오 관련 필드 추가.

**은민님**: 꽃집과는 계약 관계라서 채널 친구 추가가 가능하다. 문제 없을까?

**Claude**: 알림톡(전화번호 기반, 자동 SMS 대체발송 보장)과 친구톡(형식 자유, 템플릿 심사 불필요, 단 차단/친구끊기 시 자동 대체발송 없음)의 트레이드오프를 설명. 확인 질문 → **친구톡으로 전환**을 선택하심. 이에 따라 `manual_admin_alert` 폴백(발송 실패 시 관리자 긴급 알림)을 설계에 반영.

## 3. 2단계: API 엔드포인트 명세

`02-api-spec.md` 작성. 핵심은 `POST /api/wreath-requests`(제출 시 서버가 사전승인 규칙을 재검증하고 즉시 꽃집 발송을 트리거)와 `POST /api/webhooks/kakao-transmission`(발송 결과 콜백).

**은민님**: 증빙 없으면 422로 막는다는 게 무슨 뜻인지, 그리고 "확인 필요 사항" 3가지는 언제 알려주면 되는지 질문.

**Claude**: 422는 "요청은 정상이지만 업무 규칙상 처리 불가"를 뜻하는 HTTP 상태 코드이며, 이 경우 증빙 없이는 DB 저장도, 꽃집 전달도 되지 않고 화면에 에러 메시지만 뜬다고 설명. 확인 필요 3가지 중 1번(자진 취소 범위)은 3단계 작업 전에 필요, 2번(웹훅 중복처리)은 사실 사용자가 결정할 사항이 아니라 개발 메모, 3번(정산 항목)은 4단계 이후에 필요하다고 정리.

**은민님**: 1번 — 꽃집 전달 전까지만 자진 취소 허용. 3번 — 엑셀 추출은 반드시 필요.

**Claude**: `POST /api/wreath-requests/{id}/cancel`을 `status=submitted`일 때만 허용하도록 명시하고, `submitted_to_vendor` 이후에는 409 에러로 막도록 반영. `GET /api/admin/export`를 CSV가 아닌 xlsx 필수로 명확화하고 기본 포함 컬럼과 집계 옵션을 추가.

## 5. 배송 상태를 어떻게 아는가 — 설계상 중요한 발견

**은민님**: 꽃집에는 카톡으로 정보가 전달될 뿐인데, 우리가 어떻게 접수/배송중/완료 상태를 실시간으로 알 수 있어?

**Claude**: 친구톡은 일방향 메시지라 시스템이 스스로 상태를 알 방법이 없다는 점을 인정. 두 가지 대안(꽃집이 링크로 직접 갱신 vs 관리자가 전화 확인 후 수동 입력)을 제시.

확인 질문 → **꽃집에 원터치 링크 제공**을 선택. 상태 단계는 "카톡 전송되면 꽃집이 접수 버튼 클릭 → 접수"로 구체화.

**은민님**: (이어서) 배송완료되면 꽃집이 사진을 보내주기로 했는데, 주문건과 사진을 매칭하는 게 고민이다.

**Claude**: 카톡 채팅으로 사진을 받으면 매칭을 사람이 수동으로 해야 해서 관리자 업무가 다시 늘어난다는 문제를 짚고, 원터치 링크 페이지에서 사진을 업로드하게 하면 링크의 토큰 자체가 이미 주문을 특정하므로 매칭 문제가 사라진다고 제안.

확인 질문 → **원터치 링크 페이지에서 사진 업로드**를 선택.

이 결정에 따라 1·2·3단계 문서를 모두 소급 수정:
- 상태 값을 `submitted → submitted_to_vendor → accepted → completed`로 재정의 (`in_delivery`를 별도 DB 상태에서 제거, 화면 표시용 가상 단계로 전환)
- `wreath_requests`에 `vendor_status_token`, `accepted_at`, `completion_photo_id`, `admin_override_note` 컬럼 추가
- `attachments` 테이블을 사전승인 증빙과 배송완료 사진 겸용으로 확장 (`uploader_type` 구분)
- API 명세에 `GET/POST /api/vendor-status/{token}` 계열(로그인 없는 꽃집용 엔드포인트) 추가
- 프론트엔드 스테퍼 컴포넌트를 실제 DB 상태와 화면 표시 단계를 분리하는 방식으로 수정

## 7. 마무리 — 체크리스트 시도와 방향 전환

**은민님**: 확인 필요사항들 체크리스트를 보고 싶다고 요청.

**Claude**: 1~4단계 문서에 흩어져 있던 "확인 필요 사항"을 카테고리별(조직 정책 결정 / 외부 계약·인프라 / 꽃집 온보딩 / 프론트엔드 UX / 개발 참고사항)로 모은 체크리스트를 아티팩트(웹페이지)로 만들려 했으나, 게시가 거절됨.

**은민님**: 사실 Claude Code 창에서 개발을 시작하려 했는데 착각하고 여기서 채팅한 것 같다고 말함.

**Claude**: 문제없다고 안내하고, 이미 만든 4개 문서가 그대로 Claude Code 프로젝트의 스펙 문서로 쓰일 수 있다고 설명.

**은민님**: 문서 4개를 다시 요청 → 재전달함.

**은민님**: Claude Code로 넘어갈 때 문서 4개만 주면 되는지, 대화 전체를 복사해야 하는지 질문.

**Claude**: 문서 4개만으로 충분하다고 답변 — 대화 중 나온 결정들이 그때그때 문서에 반영되었고, 각 문서 상단에 "확정된 전제" 요약과 설계 이유가 함께 적혀 있어 문서만으로 맥락이 대부분 살아있다고 설명.

**은민님**: 감사 인사 후, 지금까지의 대화 내용을 파일로 내보내 달라고 요청 → 이 문서가 그 결과물입니다.
